# StepForward — เอกสารสรุปโครงการ

**โครงการนำร่อง TIIS · ระยะเวลา 6 สัปดาห์ · ผู้เข้าร่วม 60 คน · ทีมหลัก 3 คน · งบ 30,000 บาท**

---

## ภารกิจที่ 1 — ปัญหาที่เลือกและแนวทางที่นำเสนอ

### กลุ่มเป้าหมาย

**ผู้เริ่มทำงาน (Early-career workers)** ที่เข้าร่วมโครงการพัฒนาทักษะระยะสั้น อายุประมาณ 22–32 ปี บางคนเพิ่งเริ่มงานแรก บางคนกำลังปรับตัวกับบทบาทใหม่ในองค์กร และบางคนทำงานในสภาพแวดล้อมที่ใช้ภาษาอังกฤษหรือทักษะดิจิทัลเป็นส่วนหนึ่งของงาน

### ปัญหาที่เลือกแก้

**ทีมสนับสนุนขนาดเล็กไม่สามารถรู้ว่าใครต้องการความช่วยเหลือก่อน**

ในโครงการที่มีผู้เข้าร่วม 60 คนและทีมเพียง 3 คน ทีมไม่มีเวลาดูแลทุกคนเท่ากัน แต่ก็ไม่มีข้อมูลรวมศูนย์ที่บอกได้ว่าใคร "หยุดนิ่ง" ใครขาดความมั่นใจ หรือใครรอความช่วยเหลืออยู่ ผลคือทีมใช้เวลาติดตามด้วยการพิมพ์ถามทีละคน หรือรอให้ผู้เรียนพูดขึ้นมาเอง ซึ่งผู้เรียนที่ต้องการความช่วยเหลือมากที่สุดมักจะพูดน้อยที่สุด

### สิ่งที่รู้จริง และสิ่งที่เป็นสมมติฐาน

| สิ่งที่รู้จริงหรือสังเกตได้ | สมมติฐานที่ยังต้องตรวจสอบ |
|---|---|
| ทีม 3 คนดูแล 60 คนในเวลาจำกัด | ผู้เรียนจะเช็คอินสม่ำเสมอหากฟอร์มสั้นและง่าย |
| ผู้เรียนบางคนใช้มือถือเป็นอุปกรณ์หลัก | ระดับความมั่นใจ (1–5) สะท้อนความต้องการความช่วยเหลือได้จริง |
| ผู้เรียนที่ต้องการช่วยมักไม่ส่งสัญญาณมาเอง | กฎ priority ที่ตั้งไว้ตรงกับสิ่งที่ทีมให้ความสำคัญ |
| ทีมต้องจัดลำดับว่าจะติดตามใครก่อน | ผู้เรียนจะยอมรับให้ระบบบันทึกอุปสรรคและคำขอความช่วยเหลือ |

### ถ้าแก้ปัญหาได้ ผู้เรียนและทีมจะทำอะไรได้ดีขึ้น

- **ผู้เรียน:** ส่งสัญญาณขอความช่วยเหลือได้โดยไม่ต้องรอโอกาส ไม่รู้สึกว่าตัวเองเป็น "ปัญหา"
- **ทีม:** เปิดแดชบอร์ดได้ก็รู้ทันทีว่าวันนี้ควรติดต่อใครก่อน ไม่ต้องถามทีละคน
- **วัดผล:** อัตราการเช็คอินรายสัปดาห์, จำนวนคนที่ได้รับการติดตามภายใน 48 ชั่วโมงหลังแจ้งอุปสรรค, และระดับความมั่นใจเฉลี่ยของกลุ่มเมื่อเทียบต้นและปลายโครงการ

### 2 ทางเลือก และเหตุผลที่เลือกทางนี้

**ทางเลือกที่ 1 — Line OA / แชตบอต (ไม่ถูกเลือก)**  
ผู้เรียนส่งอัปเดตผ่าน Line แล้ว bot สรุปให้ทีม ข้อดีคือผู้เรียนใช้แพลตฟอร์มที่คุ้นเคย แต่มีข้อจำกัดคือต้องพึ่งพา API ภายนอก มีค่าใช้จ่ายซ่อนอยู่ และทีมยังไม่มีข้อมูลที่จัดลำดับได้อัตโนมัติ

**ทางเลือกที่ 2 — เว็บแอปเช็คอิน + แดชบอร์ดทีม (ที่เลือก)**  
ผู้เรียนกรอกแบบฟอร์มสั้น ระบบคำนวณ priority score อัตโนมัติ ทีมเห็นภาพรวมและรายละเอียดในหน้าเดียว เหตุผลที่เลือก: ไม่ต้องพึ่ง external service, ทำงานบนมือถือ, อธิบายกฎการจัดลำดับได้ชัดเจน และทีมสามารถ override สถานะเองได้เมื่อมีบริบทที่ระบบไม่รู้

### ใครอาจใช้งานยาก และวิธีลดอุปสรรค

| กลุ่มที่อาจมีอุปสรรค | แนวทางที่ระบบรองรับ |
|---|---|
| ผู้เรียนที่ไม่มั่นใจในการเขียน | ฟอร์มมีตัวอย่าง placeholder และฟิลด์บังคับน้อยที่สุด |
| ผู้เรียนที่ใช้มือถือ | Layout Responsive รองรับหน้าจอเล็ก |
| ผู้เรียนที่ไม่ถนัดภาษาอังกฤษ | UI มีทั้งภาษาไทยและอังกฤษ สลับได้ตลอด |
| ทีมที่มีเวลาจำกัด | แดชบอร์ดแสดง "Today / This week / When available" โดยไม่ต้องอ่านทีละคน |

## ภารกิจที่ 2 — แนวทางของชิ้นงาน และข้อจำกัด

### สิ่งที่สร้าง

**StepForward** คือต้นแบบเว็บแอปที่ทำงานได้จริงบน Next.js 15 / TypeScript โดยเลือกพัฒนา **ส่วนสำคัญหนึ่งส่วนตั้งแต่ต้นจนจบ** คือ workflow ของผู้เรียนที่เช็คอิน → ระบบบันทึกและประเมินสถานะ → ทีมเห็นผลและติดตาม

**ส่วนประกอบหลัก:**
- **Check-in form:** ผู้เรียนกรอกเป้าหมาย ความคืบหน้า ระดับความมั่นใจ (1–5) อุปสรรค และคำขอความช่วยเหลือ ระบบตรวจสอบฟิลด์บังคับ และป้องกัน submission ซ้ำด้วย idempotency key ต่อ session
- **Priority scoring:** คำนวณอัตโนมัติจากสถานะ (Urgent +5, Needs support +3), ความมั่นใจต่ำ (+3), มีคำขอช่วยเหลือ (+2), มีอุปสรรค (+1), ยังไม่ได้รับการ follow-up (+1) — คะแนน ≥7 = "Today", 4–6 = "This week", 1–3 = "When available"
- **Support dashboard:** แสดงรายชื่อผู้เรียนพร้อม priority label กรองตามสถานะ ค้นหาตามชื่อ เปิดดูประวัติ check-in และ follow-up รายคน
- **Follow-up management:** ทีมบันทึก action ที่ทำ เปลี่ยนสถานะผู้เรียน มี activity history ต่อคน
- **Persistence:** บันทึกใน localStorage พร้อม error handling หาก storage เต็มหรือถูก block มีปุ่ม restore demo data
- **i18n:** UI ภาษาไทย/อังกฤษ สลับได้ทุกหน้า ข้อมูลผู้เรียนแสดงตามที่กรอก

**Data model สำคัญ:** `Learner { id, name, status, checkIns[], followUps[] }` — CheckIn บันทึก confidence, obstacles, request พร้อม timestamp ทุกครั้ง

### ข้อจำกัดที่เหลืออยู่

| ข้อจำกัด | เหตุผลที่ยอมรับในต้นแบบนี้ |
|---|---|
| ข้อมูลไม่ซิงค์ข้ามอุปกรณ์หรือข้ามทีมงาน | localStorage เพียงพอสำหรับการสาธิต; server/DB อยู่นอกขอบเขต |
| ไม่มี authentication | โจทย์ระบุไม่ต้องสร้าง; ทีมงานใช้งานบนอุปกรณ์เดียวกันในบริบทนำร่อง |
| Demo มี 10 คน ไม่ใช่ 60 คน | เพียงพอสำหรับแสดง logic; เพิ่มได้ใน `lib/demo-data.ts` |
| กฎ priority ยังไม่ได้ตรวจสอบกับทีมจริง | เป็นสมมติฐานที่ควร validate กับทีมหลังสร้างต้นแบบ |
| check-in rate บนแดชบอร์ดเป็นค่าตัวอย่าง | ไม่มีข้อมูล attendance จริงในต้นแบบ |
